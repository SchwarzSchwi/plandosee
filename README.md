# 플랜두씨 다이어리

Supabase PostgreSQL + Vercel Serverless API + 정적 HTML/JavaScript. 데이터는 브라우저 저장소가 아닌 서버 DB에 보존됩니다.

## 설치·업그레이드

1. **새 DB:** `supabase/schema.sql` → `supabase/migrations/002_t07_security.sql` → `supabase/migrations/003_t07_observations.sql` 순서로 실행합니다. **기존 T06 DB:** 이미 T06 스키마라면 `002` → `003`만 실행합니다. T06 이전 DB만 먼저 `001_t06.sql`을 실행합니다. 각 파일은 트랜잭션이며, 일회 적용 후 성공한 마이그레이션을 재실행하지 마세요. 적용 전 백업·검증 절차는 [T07 제출문](docs/T07_SUBMISSION.md)에 있습니다.
2. `supabase/seed.sql`은 **가상 T06 데모**이며 실측 증거가 아닙니다. 운영 DB에는 넣지 마세요. 기존 무소유 자료는 비공개로 남습니다. 검증된 대상 계정을 관리자가 확인한 뒤 `supabase/transfer.sql`로 명시 이관합니다. 첫 가입자 자동 배정은 없습니다.
3. Vercel **서버** 환경 변수에 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`(또는 `SUPABASE_SERVICE_ROLE_KEY`), `APP_ORIGIN`을 등록합니다. 운영 `APP_ORIGIN`은 실제 HTTPS origin 하나(경로·끝 슬래시 없음), 로컬은 `http://localhost:3000`입니다. 미설정/다른 Origin의 변경 요청은 거절됩니다. 키에 `VITE_`/`NEXT_PUBLIC_` 접두어를 붙이지 마세요. Node 22.x를 사용합니다.
4. `npm ci`, `npm test`. 로컬 전체 앱은 Vercel 인증·프로젝트 연결 후 `npm run dev`. `.env.local`에 서버 환경 변수를 설정할 수 있습니다. 정적 출력은 `public`이며 `/api`만 DB에 접근합니다. 로컬 개발 서버는 외부에 공개하지 마세요.

## T07 인증·관찰·제출

첫 화면은 공개 로그인 화면이며 로그인 전 내 자료를 요청하지 않습니다. 가입·로그인 후에만 다이어리를 엽니다. 로그아웃/비밀번호 변경은 해당 계정의 **모든 세션**을 즉시 폐기합니다. 세션은 8시간이며 HttpOnly/SameSite=Strict 쿠키(운영 Secure), DB에는 SHA-256 digest만 저장합니다. 비밀번호 해싱은 Node/OpenSSL의 scrypt에 맡기며 세션·인증 연결은 직접 구현했습니다.

`5일 관찰`에서 시작 규칙을 고정하고 실제 서울 날짜마다 하루 한 번 0~1440 정수 분을 입력합니다. 2일차 뒤 정확한 1·2일차 ID와 이유를 가진 규칙 변경을 저장해야 3일차를 입력할 수 있습니다. 미래/과거 날짜를 입력하는 경로는 없습니다. 정확히 5일 전에는 미완료입니다. 실제 관찰을 대신 생성하지 않습니다.

**[한국어 T07 제출문·전체 기준 추적표·실행 증거·운영 절차](docs/T07_SUBMISSION.md)** — 운영 배포, 실제 자료 이관, 실제 5일 관찰, 최종 T06 제출본 확인은 별도 완료가 필요합니다.

## 데이터 구조와 API

| 모델 | DB 테이블 | 보존 값 |
| --- | --- | --- |
| Plan | `plans` | ID, 제목, 기간(시작/종료일), 우선순위, 성공 기준, 예상 분, 설명 |
| PlanRevision | `plan_versions` | 원래 계획 ID, 변경 전 **전체** JSON 스냅샷, 생성시각 |
| Todo | `tasks` | 계획 ID, 제목/내용, 마감일, 우선순위, 태그 배열, 예상 분, 현재 상태, 삭제시각 |
| ExecutionLog | `execution_logs` | 할 일 ID, 시작/종료시각, 실제 분, 막힘 이유, 종류(`work`/`completion`) |
| Retrospective | `reviews` | 계획 ID, 고칠 점 한 건, 생성시각. 숫자는 현재 DB 기록으로 계산 |

- 날짜는 `YYYY-MM-DD`, 시각은 타임존을 포함한 ISO 8601, 시간 단위는 항상 **분**입니다. 실행 입력 시각은 서울시간으로 해석하여 전송합니다. 실제 분은 서버에서 `(끝−시작)/60000`을 반올림하며 계획/할 일의 예상 값은 변경하지 않습니다.
- `/api?table=...`: GET 조회, POST 생성, PATCH 계획/할 일 수정, DELETE 할 일 논리 삭제. 서버가 허용 필드·형식·범위를 검사하며 이력은 직접 수정할 수 없습니다.
- 완료는 `PATCH /api?table=tasks&id=...`의 `{"status":"done"}`, 되돌리기는 `{"status":"progress"}`입니다. DB 트리거와 부분 UNIQUE 인덱스가 동시 요청에도 할 일당 최초 완료 이벤트를 **한 건만** 보존합니다. 이벤트는 0분이며 재개·재완료해도 추가되지 않습니다. 완료 수는 이벤트 개수가 아닌 현재 상태로 계산합니다.
- 계획 수정과 이전 값 스냅샷은 동일 DB 트랜잭션입니다. 값이 바뀌지 않은 저장은 이력을 추가하지 않습니다.
- `POST /api?action=carry-forward`에 `plan_id`, `improvement`를 보내면 돌아보기 저장과 다음 계획 생성이 함께 성공하거나 함께 취소됩니다. 다음 계획의 설명에 고칠 점 한 건이 들어가고, 기존 계획 필드를 복사한 뒤 수정 화면에서 새 기간 등을 설정할 수 있습니다.
- 삭제된 할 일과 실행 기록은 내보내기에는 보존되지만 화면 집계에서는 제외합니다.

## 돌아보기·검색 규칙

집계와 검색/필터/정렬 함수는 UI와 분리된 `public/model.js`에 있습니다.

- 계획 수: 선택한 계획에 속한 미삭제 할 일 수.
- 완료 수: 그중 **현재** `done`인 수.
- 지연 수: 미완료이면서 마감일이 `Asia/Seoul` 기준 오늘보다 앞선 수(오늘 마감·마감일 없음 제외).
- 막힘 수: 비어 있지 않은 막힘 이유가 작업 실행 기록에 하나라도 있는 할 일 수(여러 이유도 한 번만).
- 예상: 대상 할 일 예상 분의 합. 실제: 대상 할 일의 작업 실행 분 합. 차이: 실제−예상. 없는 값은 0. 최초 완료 이벤트는 0분 관리 기록이며 작업 합계에서 제외됩니다.
- 모든 집계 숫자를 누르면 해당 할 일/실행 기록을 확인합니다.
- 제목·내용·태그 검색과 상태/지연 필터를 함께 적용합니다. 마감일 오름차순(없으면 마지막) → 우선순위 높음순 → 제목 한국어순 → ID순으로 정렬합니다.

## 전체 내보내기·복원

`전체 내보내기`는 인증된 **내 소유** 엔터티(삭제 표시·이력·관찰 포함)를 단일 DB 스냅샷에서 읽은 JSON 파일 하나입니다. 비밀번호 해시와 세션은 포함하지 않습니다. 화면 로딩도 인증 후 같은 API를 사용합니다. 계정 삭제는 비밀번호 재확인 후 내 자료·이력·관찰·세션을 실제 삭제합니다. 파일 가져오기 UI는 제공하지 않습니다.

```json
{
  "version": 1,
  "exported_at": "2026-10-27T00:00:00+00:00",
  "plans": [],
  "plan_versions": [],
  "tasks": [],
  "execution_logs": [],
  "reviews": []
}
```

## 보안과 운영 한계

- **T06의 공개 무인증 API는 더 이상 현재 동작이 아닙니다.** 서버 세션 검증·DB owner scope·parent 소유권 제약으로 자료를 격리합니다. service-role 키는 RLS를 우회할 수 있으므로 탈취 시 위험하며 서버에만 둡니다. 일반 브라우저 DB 역할에는 인증 테이블·세션·RPC 접근 권한이 없습니다.
- 사용자 문자열은 DOM 텍스트 노드/입력 값으로만 표시하며 사용자 입력을 `innerHTML`에 넣지 않습니다. 로그인 복원에 쓰는 HTML은 정적 로그인 마크업뿐입니다. 스크립트 형태 문자열도 그대로 저장·표시됩니다. 배포 CSP는 외부/인라인 스크립트 실행을 차단합니다.
- DB 오류 원문과 서버 키는 응답·콘솔로 출력하지 않습니다. `.env*`, 의존성, Vercel 로컬 설정은 Git에서 제외합니다. 노출된 키가 있다면 파일 삭제만으로 해결되지 않으므로 즉시 폐기·교체하고 별도로 이력을 정리해야 합니다.
- `npm run audit:secrets`는 작업 파일·로컬에서 도달 가능한 전체 Git 이력·존재하는 정적 산출물을 패턴 검사하며 값 자체는 출력하지 않습니다. 원격 배포·삭제된 ref·운영 로그·모든 종류의 비밀을 완전히 검증하는 도구는 아닙니다.
- 전체 JSON을 메모리에서 처리하므로 대량 데이터에서는 Vercel/Supabase 응답 크기·시간 제한에 도달할 수 있습니다.

## 검증

- `npm test`: Node 기본 테스트 러너로 API 입력·상태 요청·오류 비노출, 서울 자정 경계, 집계/0 기본값, 검색·필터·정렬 검증.
- PostgreSQL 서버 도구가 있으면 `npm test`가 임시 격리 DB에서 `test/database.sh`·`test/database.sql`도 실행합니다(도구가 없거나 root면 명시적으로 skip). 완료 중복·동시 요청·재개·재완료, 이력, 제약조건, 이월, 내보내기, 데모 데이터를 검사하며 임시 파일은 `/tmp`에서 정리합니다.
- 자동 테스트의 모의 API, 실제 격리 PostgreSQL, 운영 배포 확인을 구분한 결과는 제출문을 참고하세요. 이전 T06 브라우저 확인은 T07 운영 확인의 근거로 재사용하지 않습니다.
- 실제 호스팅 Supabase/Vercel 연결은 자격증명 부재로 검증하지 못했습니다. 배포 전 스키마/마이그레이션 적용 및 서버 키 설정 후 새로고침·내보내기를 확인해야 합니다.
- `@supabase/supabase-js` 2.118.0, Vercel CLI 48.12.1을 lockfile과 함께 고정했습니다. 운영 의존성 감사는 0건이지만 Vercel CLI 개발 전이 의존성에는 경고가 남아 있습니다. CLI 최신 메이저도 감사 경고가 있어 무작정 업그레이드하지 않았습니다. 개발 도구 입력은 신뢰된 로컬 프로젝트로 제한하고 운영 앱에서 CLI를 실행하지 마세요.
